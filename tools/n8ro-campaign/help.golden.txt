n8ro-campaign - EXT-17 headless campaign runner (milestone 5: execution, the
                determinism gate and one parameterisation axis; nothing is
                judged until milestone 6)

usage: n8ro-campaign run-once  --out-dir <dir> [options]
       n8ro-campaign repeat    --out-dir <dir> --count <n> [options]
       n8ro-campaign repeat    --out-dir <dir> --campaign <file> [options]
       n8ro-campaign self-test --out-dir <dir> [options]
       n8ro-campaign --help

commands:
  run-once                 execute one run into <out-dir>/runs/<run-id>. One run is not a
                           campaign, so it does not self-test.
  repeat                   run the determinism self-test, then execute the campaign,
                           continuing past a run that fails, and write a campaign
                           summary carrying the self-test's result. Without
                           --campaign that is --count runs of one configuration;
                           with it, one run per declared parameter value.
  self-test                run the determinism self-test alone and stop. The campaign does
                           NOT get its gate from this command - repeat runs it itself, so
                           that it is never something anyone has to remember (CR-DET-1).

the determinism self-test (CR-DET-1, and step 4 of the brief - a HARD GATE):
  Two runs of one configuration, executed into <out-dir>/selftest/runs/000 and 001 - which
  are NOT campaign runs and are never counted among the campaign's outcomes - and compared
  two ways. Both comparisons always run and both are always reported:

    content   per (entity, occupancy) value sequences aligned on sim_time_s, over RUNNING
              segments only. A sample present in one run and absent from the other is NOT
              a difference: this platform publishes a slightly different subset of frames
              every run. It is counted and reported.
    bytes     byte for byte, with platform.model_path excluded - the one field the capture
              format names as legitimately host-dependent. EXPECTED TO FAIL here, and never
              engineered to pass.

  Which of the two decides is OQ-2, out with the owner of the brief and UNANSWERED. A pass
  on the content basis does NOT discharge the brief's acceptance criterion 2 as written; it
  discharges it under the content reading, which is this project's own named deviation.
  A campaign whose self-test does not pass executes no campaign run at all.

  --gate-basis <b>         content (default) or bytes. Selects which comparison decides.
  --coverage-floor <p>     whole percent of the smaller run's comparable samples that must
                           be present in BOTH, or the verdict is indeterminate rather than
                           pass - a comparison whose intersection collapsed would otherwise
                           report that everything it compared agreed. Default 99. Measured
                           over all 190 pairs of M2's twenty runs: worst 0.4192% unmatched.

the run:
  --out-dir <dir>          campaign directory. Runs land in <dir>/runs/NNN. Required.
  --scenario <name>        scenario to load. Default "Atacama Air Defense".
  --model-name <name>      model the scenario lives in. Default N8roSimSchema.
  --model-path <dir>       schema and instance database. Default C:\N8RO\data\db.
  --schema-file <name>     schema name inside that database. Default N8roSimSchema.
  --count <n>              repeat only: how many runs of ONE configuration. Default 20.
                           Cannot be combined with --campaign, where the number of
                           runs is the number of values the axis declares.
  --first-run <n>          repeat only: ordinal of the first run. Default 0.

the parameterisation axis (CR-PAR-1, and step 5 of the brief):
  --campaign <file>        a JSON file declaring the ONE axis this campaign varies,
                           and the values it takes. Changing what a sweep varies is
                           an edit to this file and no rebuild. repeat only.

  [B]: "One axis done properly beats four done loosely." Which axis is OQ-4, and it
  is DECIDED - initial positions and velocities, as one declared scalar applied to
  named entities before start. The measurement that decided it, including the axis
  range's own fidelity ceiling, is in docs/m5-oq4.md.

  {
    "axis": {
      "name": "red_raid_speed_ms",      label in every run record and in the report
      "kind": "velocity_ned_scaled",    velocityNed = direction * value
      "applies_to": "velocityNed magnitude",       free text, for the report
      "units": "m/s",                             free text, for the report
      "entity_groups": [
        { "direction_ned": [-1, 0, 0], "names": ["RedUAV_N_01", "RedUAV_N_02"] },
        { "direction_ned": [0, -1, 0], "names": ["RedUAV_E_01"] }
      ],
      "values": ["11", "27.5", "55", "110", "220"],
      "self_test_value": "55"           optional; defaults to the first value
    }
  }

  Entities are NAMED, never matched. There is no glob: resolving one would mean
  subscribing the control path to sim/entity/state, which would perturb the very
  publication schedule the determinism gate measures - and a pattern that silently
  matches nothing is the failure this project keeps finding. A named entity that
  carries no sample in a run's own capture is reported in that run's record.

  A value is carried as the TEXT you wrote it as, into the run record and into the
  report. The double derived from it exists to publish it and to order the sweep,
  and is never printed - a re-formatted double would put CR-DET-2's locale hazard
  back on a path the build searches for it.

  self_test_value is the value the determinism gate runs at. CR-DET-1 says "the
  same configuration twice" and a sweep has many, so the gate runs at ONE of them,
  and it establishes determinism FOR THAT VALUE. It is one claim at a named point,
  not one per run, and the report says so. Both gate runs are copies of one
  configuration, which is what makes them a valid pair (CR-PAR-1).

  Two runs at DIFFERENT values are never compared. They are two configurations, and
  a gate over them would report a difference meaning only that the sweep worked.

the end of a run:
  --frames <n>             stop predicate: a run is finished when the engine's frame
                           number, as published on sim/engine/state, reaches n.
                           Default 1200. No wall-clock quantity participates.
  --run-timeout-ms <n>     backstop, never the definition of the end. A run that hits it
                           is reported as timeout - its own outcome, neither pass nor
                           fail. There is no way to run unbounded. Default 600000.

bring-up timeouts (each bounds one observed condition; none is a delay):
  --ready-timeout-ms <n>   host publishes engine state. Default 60000.
  --load-timeout-ms <n>    scenario reports loaded. Default 120000.
  --start-timeout-ms <n>   engine reports running. Default 30000.
  --stop-timeout-ms <n>    engine leaves running after stop. Default 30000.
  --host-exit-timeout-ms <n>      host exits after being asked. Default 20000.
  --recorder-exit-timeout-ms <n>  recorder closes its capture after host loss, which it
                           detects after 3.0 s of engine-state silence. Default 30000.

processes:
  --host-exe <path>        headless host. Default C:\N8RO\bin\n8ro-sim-app.exe.
  --recorder <path>        capture recorder, driven as a process. Required unless
                           --no-recorder.
  --no-recorder            run without recording. The run still executes and is still
                           recorded in run.json; there is simply no capture.
  --sim-config-host <e>    host-side config entry. Default SimEngineHost_SharedMemory.
  --sim-config-client <e>  client-side config entry. Default SimEngineClient_SharedMemory.
  --capture-max-bytes <n>  per-capture byte bound, passed to the recorder. Default:
                           61000 x --frames, which is three times the measured
                           per-frame capture cost - a bound that does not fire on
                           a normal run and does fire on a runaway. Pass 0 for
                           unbounded. A campaign-level ceiling is not this; that
                           is --disk-ceiling-bytes below.
  --on-size-limit <a>      stop (default, and OQ-6's decision) or rotate, on reaching
                           --capture-max-bytes. rotate keeps the run's tail and makes
                           the capture a SET of files whose segment ordinals restart
                           in every part - measured at M3 to turn one run's two
                           segments into five (part, segment) keys. stop keeps one
                           file per run and loses the tail, and says so in the file
                           and in run.json's capture.covers_whole_run.

disk (CR-CAP-5; the upstream bound above is per file, this one is per campaign):
  --disk-ceiling-bytes <n> ceiling over the WHOLE campaign directory, captures and logs
                           together. Default 8589934592 (8 GiB). Checked against free
                           space before run 1 and against actual usage after every run;
                           reaching it stops the campaign with a named outcome and
                           leaves every completed run valid. 0 disables the ceiling.
  --bytes-per-frame <n>    the projection used by the pre-flight check. Default 25400,
                           measured over M2's twenty runs: 24.3 MB of capture plus
                           5.4 MB of host log per 1200-frame run.

environment (both are measured preconditions, not preferences):
  --n8ro-release <dir>     N8RO_RELEASE for the child processes. Default C:\N8RO.
                           Without it the host skips its plugin scan, never registers
                           componentPhysics, and refuses every 42-entity scenario load
                           while sitting idle rather than failing.
  --path-prepend <dir>     prepended to PATH for the child processes, and needed by this
                           binary too. Default C:\N8RO\bin. Without it an SDK-linked
                           binary does not load at all.

other:
  --query-catalogue        query the scenario catalogue over the bus during bring-up and
                           log what it answers.
  --queue-size <n>         recorder handler-to-writer queue bound, in records. Omitted
                           leaves the recorder's own default in place. A small value
                           deliberately overloads it so that a capture's
                           trailer.drops.samples_not_recorded becomes non-zero - which is
                           the only way to exercise CR-DET-1's rule that such a capture is
                           EXCLUDED from the comparison rather than diffed. Nothing this
                           project has run has ever dropped a sample at the default.
  --help                   this text.

exit codes:
  0  every run completed - the stop predicate was satisfied and teardown was clean
  1  at least one run did not complete (timeout or infrastructure error), or the
     campaign stopped at its disk ceiling
  2  usage or configuration error; no run was attempted
  3  the determinism self-test did not pass, and NO campaign run was attempted. Step 4 of
     the brief: "Do not build further until it passes." Whether the gate FAILED or could
     not be established at all - a self-test run that did not complete has established
     nothing about determinism and is not a determinism failure - is named in
     <out-dir>/selftest/self-test.json under "outcome"
